# HTTP란?

: 서버와 클라이언트가 서로 데이터를 주고받기 위해 사용되는 프로토콜

### 역할

: 웹 브라우저와 서버 간 데이터 요청 및 응답 처리.

## HTTP/1.1

- 현재 가장 많이 사용하며, 대부분의 기능이 추가
- Persistent connection: 지정한 timeout동안 연속적인 요청 사이에 connection을 닫지 않음
- Pipelining: 응답을 기다리지않고 순차적인 요청을 연속적으로 보냄. Head of Line Blocking 발생
- Head of Line Blocking: 우선순위로 들어온 요청의 응답 시간이 길어지면 후순위에 있는 요청의 응답 시간도 길어짐
- 대부분의 기능은 1.1에 구현되어있고, 2와 3에서는 성능 개선에 초점이 맞춰짐

## HTTP/2.0

- 메세지 전송 방식의 변화
- 파싱, 전송속도 증가
- 멀티 플렉싱
- HPACK 압축: 헤더 중복값 개선

## HTTP/3.0

- UDP 기반의 QUIC 프로토콜 바탕으로 제작
- 기존 TCP의 고질적인 지연시간(RTT)를 해결

# HTTP의 통신구조

- 클라이언트와 서버로 나누어진 구조 → 각자의 역할에 집중하기 위해
- 클라이언트가 서버에 요청을 보내고 서버가 응답을 반환

# HTTP의 무상태성(Stateless)

: 클라이언트와 서버 사이에 상태를 유지하지 않는다.

- 서버가 클라이언틍틔 상태를 보존하지 않음.
- 클라이언트가 상태 정보를 갖고 있기 때문에, 아무서버나 호출해도 돼서 서버의 스케일아웃에 유리
- stateful보다 데이터를 많이 사용한다.

## Stateful

: 서버가 클라이언트의 상태를 보존

- 서버가 장애나면 클라이언트는 처음부터 다시 작업을 요청해야함
- 서버가 바뀔때마다 클라이언트의 내용을 기록해서 상태를 유지해야함

# HTTP의 비연결성(Connectionless)

: HTTP는 기본이 연결을 유지하지 않는 모델

- 서버와 클라이언트의 connection 연결을 지속하지 않음
- 1시간동안 수천명 이상이 서비스를 사용해도 실제 서버에서 동시에 처리하는 요청은 수십개 이하
- 서버 자원을 효율적으로 사용가능
- TCP/IP 연결을 매번 새롭게 맺어야하므로, 시간이 걸린다 → 현재는 HTTP 지속 연결로 해결
- HTTP/2, HTTP/3에서 최적화

## 비연결성의 한계 - 단기 커넥션

- HTTP 초기 - 연결, 종료 낭비
- 새로 연결을 맺을 때마다 TCP Handshake가 발생
- HTTP 초기에는 모든 자료에 대해 비연결성으로 각각의 자원에 대해 연결/응답/종료를 반복하다보니 1초가량 소모됨

## 비연결성 극복 - HTTP 지속 연결

- 클라이언트는 서버와 소켓 연결을 한 다음 필요한 자원을 요청/응답으로 다운받음
- 소켓을 일정시간동안 더 유지함으로써, 필요한 자원들을 모두 다운로드 받을 때까지 연결이 종료되지 않고 요청/응답이 반복된 뒤 종료

# HTTP 상태 코드

: 클라이언트가 보낸 요청의 처리 상태를 응답에서 알려주는 기능

- 1xx(정보): 요청을 받았으며 프로세스를 계속 진행
- 2xx(성공): 요청을 성공적으로 받았으며 인식했고 수용
- 3xx(리다이렉션): 요청 완료를 위해 추가 작업 조치가 필요
- 4xx(클라이언트 오류): 요청의 문법이 잘못되었거나 요청을 처리할 수 없음
- 5xx(서버 오류): 서버가 명백히 유효한 요청에 대해 충족을 실패

# HTTP 메세지

## HTTP 메세지 구조

- 시작 라인
- 헤더
- 공백 라인: HTTP 메세지 값 구분을 하기 위한 라인. 반드시 있어야한다.
- 바디: HTTP 요청 종류에 따라 있을 수도 있고 없을 수도 있음.

## HTTP 요청 메세지

### 시작 라인

- Method: GET / POST / PUT / DELETE 등
- URL: 요청 대상 경로 표시
- Version: 사용된 http 버전

### 헤더

- HTTP 전송에 필요한 모든 부가 정보를 담고 있다. (메세지 크기, 압축 여부, 인증, 브라우저 정보, 서버 정보, 캐시 ..등)
- Host, User-Agent, Accept

### 공백라인

: 헤더와 바디를 구분하기 위한 라인

### 바디

: 실제 전송할 데이터 (HTML 문서, 이미지, 영상, JSON등 )

## HTTP 응답 메세지

### 시작 라인

- Version: 사용된 http 버전
- Status Code: 클라이언트가 보낸 요청이 성공인지 실패인지 숫자 코드로 나타냄
- Status Message: Status Code에 대한 결과를 글로 표현

### 헤더

: HTTP 전송에 필요한 모든 부가 정보를 담고 있음

- Content-Type, Cache-Control, Set-Cookie

### 공백라인

: 헤더와 바디를 구분하기 위한 라인

### 바디

: 전송받은 데이터

# HTTP 메서드

## HTTP 메서드 종류

- GET: 리소스 조회
- POST: 요청 데이터 처리
- PUT: 리소스를 대체, 해당 리소스가 없으면 생성
- PATCH: 리소스를 일부만 변경
- DELETE: 리소스 삭제

---

- HEAD: GET과 동일하지만 메시지 부분을 제외하고 상태줄과 헤더만 반환
- OPTIONS: 대상 리소스에 대한 통신 가능 옵션을 설명(CORS에서 사용)
- CONNECT: 대상 자원으로 식별되는 서버에 대한 터널을 설정
- TRACE: 대상 리소스에 대한 경로를 따라 메세지 루프백 테스트를 수행

## HTTP 메서드 특성

### 안정성

- 호출해도 리소스 변경이 일어나지 않는 속성
- GET, HEAD가 안전한 메소드

### 멱등성

- 동일한 요청을 여러번 보내도 한번 보내는 것과 같은 것
- 요청의 결과를 보고 판단
- Timeout등으로 클라이언트가 서버로부터 정상 응답을 받지 못했을 때 같은 요청을 다시 해도되는지 판단하는 근거
- GET, PUT, DELETE
- POST는 멱등이 아님. 두 번 호출하면 에러가 발생할 수 있다.

### 캐시 가능

- 응답 결과를 캐시해 사용할 수 있는 속성
- GET, HEAD, POST, PATCH가 가능하나, Message Body의 캐시 키의 복잡성 문제로 실제로는 GET, HEAD만 사용

# HTTP DDos

### HTTP Flood

: 다수의 봇(봇넷)을 사용하여 대상 서버에 과도한 HTTP 요청(GET 또는 POST)

- 봇이 대규모로 `/homepage`나 `/login` 페이지를 요청하여 서버 리소스를 소모.

→ 서버가 모든 요청을 처리하지 못해 속도 저하 또는 서버 다운.

### Slowloris

: HTTP 요청을 비정상적으로 천천히 보내, 서버의 연결 자원을 고갈

- 요청을 끝내지 않고, 지속적으로 새로운 요청을 보내 서버가 연결을 닫지 못하도록 유도.

→ 서버가 과도한 연결을 처리하지 못하고 다운.

### 방어

- **트래픽 필터링**
  - WAF(Web Application Firewall)를 사용하여 비정상적인 HTTP 요청 필터링.
- **Rate Limiting**
  - 클라이언트당 요청 수를 제한하여 과도한 트래픽을 차단.
- **CDN(Content Delivery Network)**
  - 글로벌 네트워크를 사용하여 트래픽을 분산시켜 DDoS 공격을 완화.

# HTTP vs HTTPS

### HTTP

: 데이터 전송이 암호화되지 않음

### HTTPS

- SSL/TLS를 통해 데이터를 암호화하여 전송
- 보안이 중요한 페이지 에서 사용

# HTTP의 보안

- CORS: 다른 도메인에서 리소스를 요청할 떄의 보안 정책
- 쿠키와 세션: 상태를 유지하고 사용자 정보를 저장하기 위한 방식
- CSRF/XSS: HTTP 기반의 보안 취약점 및 방어 방법
