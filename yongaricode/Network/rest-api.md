# REST API란

## REST API

: 소**프트웨어 프로그램 아키텍처의 한 형식으로** 자원을 이름 (자원의 표현) 으로 구분하여 해당 자원의 상태 (정보)를 주고 받는 모든 것을 의미

- 기본적으로 웹의 기존 기술과 **HTTP 프로토콜을 그대로 활용**하기 때문에 **웹의 장점을 최대한 활용할 수 있는 아키텍처 스타일**

## REST의 구성요소

### 자원

: 소프트웨어가 관리하는 모든 것을 의미

- 고유한 식별자, 즉 URI를 통해 접근 가능

### 행위

: 클라이언트가 자원에 대해 어떤 작업을 수행할지

- HTTP 메서드(POST, GET, PUT, DELETE)를 사용하여 자원과 상호작용을 정의

### 표현

: 자원의 상태를 나타내는 데이터로, 주로 JSON이나 XML 형식으로 표현됨.

- 클라이언트와 서버는 표현을 주고받으며 자원의 상태를 전달

⇒ REST란 HTTP URI를 통해 자원을 명시하고, `HTTP Method (POST, GET, PUT, DELETE)`를 통해 해당 자원에 대한 `CRUD OPERATION`을 적용하는 것을 의미한다.

## **REST 특징**

### **1. 클라이언트 / 서버 구조**

- 클라이언트는 유저와 관련된 처리를, 서버는 REST API를 제공함으로써 각각의 역활이 확실하게 구분되고 일괄적인 인터페이스로 분리되어 작동할 수 있게 한다.
- REST Server: API를 제공하고 비지니스 로직 처리 및 저장을 책임진다.
- Client: 사용자 인증이나 context (세션, 로그인 정보) 등을 직접 관리하고 책임진다.
- 서로 간 의존성이 줄어든다.

### **2. 무상태성 (Stateless)**

- REST는 HTTP의 특성을 이용하기 떄문에 무상태성을 갖는다.
- 즉 서버에서 어떤 작업을 하기 위해 상태정보를 기억할 필요가 없고 들어온 요청에 대해 처리만 해주면 되기 때문에 구현이 쉽고 단순해진다.

### **3. 캐시 처리 가능 (Cacheable)**

- HTTP라는 기존 웹표준을 사용하는 REST의 특징 덕분에 기본 웹에서 사용하는 인프라를 그대로 사용 가능하다.
- 대량의 요청을 효율적으로 처리하기 위해 캐시가 요구된다.
- 캐시 사용을 통해 응답시간이 빨라지고 REST Server 트랜잭션이 발생하지 않기 때문에 전체 응답시간, 성능, 서버의 자원 이용률을 향상 시킬 수 있다.

### **4. 자체 표현 구조 (Self - descriptiveness)**

- JSON을 이용한 메시지 포멧을 이용하여 직관적으로 이해할 수 있고 REST API 메시지만으로 그 요청이 어떤 행위를 하는지 알 수 있다.

### **5. 계층화 (Layered System)**

- 클라이언트와 서버가 분리되어 있기 때문에 중간에 프록시 서버, 암호화 계층 등 중간매체를 사용할 수 있어 자유도가 높다

### **6. 유니폼 인터페이스 (Uniform Interface)**

- Uniform Interface는 Http 표준에만 따른다면 모든 플랫폼에서 사용이 가능하며, URI로 지정한 리소스에 대한 조작을 가능하게 하는 아키텍쳐 스타일을 말한다
- URI로 지정한 Resource에 대한 조작을 통일되고 한정적인 인터페이스로 수행한다.
- **즉, 특정 언어나 기술에 종속되지 않는다.**

## 중심규칙

- URI는 정보의 자원을 표현해야 한다
- 자원에 대한 행위는 HTTP Method (GET, POST, PUT, DELETE 등)으로 표현한다

## 세부규칙

**1. 슬래시 구분자 ( / )는 계층 관계를 나타내는데 사용한다.**

**2. URI 마지막 문자로 슬래시 ( / )를 포함하지 않는다.**

**3. 언더바 대신 하이픈을 사용한다.**

**4. URI는 동사보다는 명사를, 대문자보다는 소문자를 사용하여야 한다.**

**5. 파일확장자는 URI에 포함하지 않는다.**

**5. 리소스 간에는 연관관계를 계층화 시켜서 표현한다.**

## REST의 설계 목표

1. **컴포넌트 간 유연한 상호 연동성 확보**
   - 표준화된 HTTP와 URI 사용으로 어디서나 일관된 방식으로 작동.
2. **범용 인터페이스**
   - HTTP와 URI를 통해 표준화된 범용 인터페이스 제공.
   - 개발자는 비즈니스 로직에만 집중 가능.
3. **컴포넌트의 독립적 배포**
   - 규격에 따라 개발 시, 새로운 컴포넌트 추가에도 연동 문제 없음.
4. **중간 컴포넌트의 역할 수행**
   - 클라이언트와 엔드 서버 간 중계 역할.
   - 지연 감소, 보안 강화, 레거시 시스템 인캡슐레이션 가능.

# RESTful API

## **RESTful**

- REST API를 제공하는 웹 서비스.

## **RESTful API 개발 원칙**

- **자원의 식별 가능성**
  - URL만으로 자원의 종류와 위치를 명확히 알 수 있어야 함.
  - 데이터는 JSON 또는 XML 형태로 HTTP body에 포함.
- **명시적 행위**
  - HTTP 메소드를 활용하여 명확한 행위 표현 (e.g., GET, POST, PUT, DELETE).
  - REST 아키텍처의 기본 원칙 준수.
- **자기 서술적 데이터**
  - 메타정보만으로 데이터의 성격과 처리를 위한 실행 정보를 알 수 있어야 함.
- **HATEOAS (Hypermedia as the Engine of Application State)**
  - 서버가 클라이언트에게 링크를 제공하여 추가 정보 탐색 가능.
  - 서버와 클라이언트를 독립적으로 발전 가능하도록 지원.

## **REST의 단점들**

- **표준의 부재**
  - REST는 설계 원칙에 불과하며, 자체 표준이 없어 개발자 간 정의와 합의가 필요.
- **Point-to-Point 통신 의존**
  - 서버와 클라이언트가 직접 연결되는 구조로, 일부 어플리케이션에는 부적합.
- **통신 및 정책 관련 지원 부족**
  - 보안 및 통신규약 관련 설계와 구현은 개발자의 몫.
- **HTTP 의존성**
  - HTTP 외의 프로토콜에서는 자연스러운 구현이 어려움.
  - 그러나 웹 통합 환경에서는 큰 단점이 되지 않음.
- **제한된 HTTP 메소드**
  - CRUD 4가지 메소드만으로는 일부 표현이 모호.
